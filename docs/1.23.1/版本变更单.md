## 二、变更背景

【sendemail 获取 jobId 缓存优化（REQ-DSS-1.23.1-001）】
sendemail 节点执行时从 CS（ContextService）获取上游节点 jobIds（`EmailCSHelper.getJobIds`），每次调用需 1 次 contextID 解析 + 每个上游节点 2 次 CS 远程查询，且同一次执行内多处入口（邮件内容生成 `MultiContentEmailGenerator`、`getJobTypes`）会重复触发整条查询链，CS 压力与节点时延随上游节点数线性放大，CS 抖动时节点失败概率成倍增加。本期在单次节点执行内增加 jobIds 缓存，首次加载后复用，执行结束统一清理，行为语义零变化。

【其余需求】
暂无。`dev-1.23.1` 当前仅含本项变更（分支首个提交即 ccdfadfc6），后续追加需求时更新本单。

## 三、变更内容（新增功能/优化项）

### 1. 系统变更

【sendemail 获取 jobId 缓存（REQ-DSS-1.23.1-001）】
- `EmailCSHelper.getJobIds` 增加执行内缓存：以 runtimeMap 为载体（key `__dss_sendemail_job_ids_cache__`，value `JobIdsCache(Array[Long])`），`runtimeMap.synchronized` 保证线程安全（同执行并发调用仅一个线程加载 CS，其余命中缓存）。
- 缓存副本防御：写入与命中返回均为 `clone()`，调用方修改返回数组不污染缓存。
- 原 CS 加载链原样抽为私有 `loadJobIds`（content 解析、getNodeNameByNodeID、getLinkisJobData、80003 空结果集异常均逐行保留），加载失败不写缓存，可重试。
- `SendEmailRefExecutionOperation.execute` 以 `Utils.tryFinally` 包装（原执行体抽为 `executeWithJobIdsCache`，逻辑不变），节点执行结束（成功/失败/异常）调用新增的 `EmailCSHelper.clearJobIdsCache` 清理缓存，跨执行不残留。
- 收益：一次执行内 K 次获取、M 个上游节点时，CS 远程调用由 K×(1+2M) 次降为 1×(1+2M) 次。

## 十二、变更后验证方法

- 缓存生效：以多上游节点（≥2）工作流执行 sendemail 节点，节点日志中 `From cs to getJob ids` 至多出现 1 次；执行内多次获取时出现 `From sendemail execution cache to get Job IDs`。
- 行为一致：邮件附件（图片/HTML）内容、收件人、节点状态与升级前版本完全一致；content 为空/CS 空结果仍报 80003（empty result set is not allowed）。
- 生命周期：节点成功与失败（如 SMTP 异常）两种路径执行结束后，runtimeMap 中均无 `__dss_sendemail_job_ids_cache__`；重试执行重新走 CS 加载。
- 回归：存量 sendemail 工作流（含 sendFeishu=true 的 DataGo 外发节点）原样执行，投递行为不变。
