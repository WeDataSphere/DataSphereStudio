# 数据服务批量审批与增量授权功能需求文档

## 一、需求背景

### 1.1 现状分析

**当前提单流程**：
1. 用户创建或更新API，生成新版本（未提单状态）
2. 用户选择API，填写审批单信息（包括授权用户、授权期限等）
3. 系统向DM发起提单
4. 用户手动调用刷新接口，检查审批状态
5. 审批通过后，用户在页面点击刷新按钮，调用 `approvalRefresh` 接口生成Token（已实现）

**当前存在的问题**：
1. API可被重复申请，但每次申请都需要填写全部的授权用户
2. 如果一个API已经审批通过，需要新增授权用户时，用户需要：
    - 更新API创建新版本
    - 重新填写所有授权用户（包括已有的和新增的）
    - 重新提交审批
3. 用户体验差，操作繁琐，容易遗漏用户
4. 审批通过后，没有自动生成Token的机制

### 1.2 需求目标

实现数据服务的**增量授权功能**：
1. 支持批量选择单个或多个API进行提单
2. **自动获取API的历史授权用户**（基于运行中的版本）
3. 用户只需要填写新增的授权用户
4. 系统自动合并历史用户 + 新增用户（去重）
5. **保留用户填写的原始授权用户信息**（不包含历史用户）
6. 审批通过后，自动为所有用户生成Token

```java
/**
 * 查询API历史授权用户
 */
public Map<String, Object> queryApiHistoryUsers(Long apiId, Long apiVersionId) {
    // 1. 查询API基本信息
    ApiServiceVo apiService = apiServiceDao.queryById(apiId);
    if (apiService == null) {
        throw new ApiServiceQueryException(800999, "API不存在");
    }

    // 2. 确定查询的版本
    Long targetVersionId = apiVersionId;
    ApiVersionVo apiVersionVo;

    if (targetVersionId == null) {
        // 未指定版本，查询运行中版本
        apiVersionVo = apiServiceVersionDao.queryApprovedVersionByApiId(apiId);
        if (apiVersionVo == null) {
            throw new ApiServiceQueryException(800999, "该API没有运行中的版本");
        }
        targetVersionId = apiVersionVo.getId();
    } else {
        // 指定了版本，直接查询
        apiVersionVo = apiServiceVersionDao.queryApiVersionByVersionId(targetVersionId);
    }

    // 3. 查询该版本的授权用户
    List<TokenManagerVo> tokenList = apiServiceTokenManagerDao
        .queryByVersionIdWithValidStatus(targetVersionId, ApiCommonConstant.API_ENABLE_STATUS);

    // 4. 组装返回结果
    Map<String, Object> result = new HashMap<>();
    result.put("apiId", apiId);
    result.put("apiName", apiService.getName());
    result.put("apiVersionId", targetVersionId);
    result.put("version", apiVersionVo.getVersion());
    result.put("users", tokenList);

    return result;
}
```

#### 5.2.1 实现位置

#### 5.2.2 Service层实现

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void submitToDm(ApiSubmitVo apiSubmitVo) throws Exception {
    String approvalNo = UUIDGenerator.genUUID();
    List<ApiVersionVo> submitApiVersionList = new ArrayList<>();

    // [新增] 增量授权逻辑
    if (apiSubmitVo.isIncrementalMode()) {
        // 1. 保存用户填写的原始授权用户信息（不包含历史用户）
        apiSubmitVo.setOriginalApplyUser(apiSubmitVo.getApplyUser());

        // 2. 自动合并历史用户 + 新增用户
        List<String> allUsers = mergeIncrementalUsers(apiSubmitVo);
        apiSubmitVo.setApplyUser(String.join(",", allUsers));

        LOG.info("增量授权模式，原始用户：{}，合并后用户列表：{}",
            apiSubmitVo.getOriginalApplyUser(), apiSubmitVo.getApplyUser());
    }

    // 3. 原有逻辑：处理每个API版本
    for (ApiVersionIdVo apiVersionIdVo : apiSubmitVo.getSubmitApiInfos()) {
        ApiServiceVo apiServiceVo = apiServiceDao.queryById(apiVersionIdVo.getApiId());
        ApiVersionVo apiVersionVo = apiServiceVersionDao.queryApiVersionByVersionId(apiVersionIdVo.getApiVersionId());
        apiVersionVo.setScriptPath(apiServiceVo.getScriptPath());
        submitApiVersionList.add(apiVersionVo);
        apiVersionVo.setAuthId(approvalNo);

        // 更新auth_id
        apiServiceVersionDao.updateAuthIdByapiVersionId(apiVersionVo.getId(), approvalNo);

        // 每个api version加一条approval记录（包含original_apply_user）
        addApprovalToDB(apiServiceVo, apiVersionVo, apiSubmitVo);
    }

    // 4. 发起dm提单
    sendApprovalToDM(approvalNo, apiSubmitVo, submitApiVersionList);

    // 5. 修改为已提单状态
    submitApiVersionList.forEach(apiVersionVo -> {
        apiServiceVersionDao.updateApiVersionStatusById(apiVersionVo.getId(), ApiVersionStatusEnum.SUBMITTED.getIndex());
    });
}

/**
 * 合并增量授权用户
 * 核心逻辑：合并历史用户 + 新增用户，去重后返回
 * 增量模式下总是合并
 */
private List<String> mergeIncrementalUsers(ApiSubmitVo apiSubmitVo) {
    Set<String> allUsers = new LinkedHashSet<>();

    for (ApiVersionIdVo apiVersionIdVo : apiSubmitVo.getSubmitApiInfos()) {
        // 1. 查询运行中版本的历史用户
        ApiVersionVo runningVersion = apiServiceVersionDao.queryApprovedVersionByApiId(
            apiVersionIdVo.getApiId()
        );

        List<String> existingUsers = new ArrayList<>();
        if (runningVersion != null) {
            // 2. 查询该版本的有效Token用户
            List<TokenManagerVo> tokenList = apiServiceTokenManagerDao
                .queryByVersionIdWithValidStatus(runningVersion.getId(), ApiCommonConstant.API_ENABLE_STATUS);
            existingUsers = tokenList.stream()
                .map(TokenManagerVo::getUser)
                .distinct()
                .collect(Collectors.toList());
        }

        // 3. 解析用户填写的用户列表（新增用户）
        List<String> submittedUsers = new ArrayList<>();
        if (StringUtils.isNotBlank(apiSubmitVo.getApplyUser())) {
            submittedUsers = Arrays.stream(apiSubmitVo.getApplyUser().split(","))
                .map(String::trim)
                .filter(StringUtils::isNotBlank)
                .distinct()
                .collect(Collectors.toList());
        }

        // 4. 合并用户（历史用户 + 新增用户，去重）
        allUsers.addAll(existingUsers);
        allUsers.addAll(submittedUsers);

        LOG.info("API {} 增量授权，历史用户：{}，新增用户：{}，合并后：{}",
            apiVersionIdVo.getApiId(), existingUsers, submittedUsers, allUsers);
    }

    return new ArrayList<>(allUsers);
}
```

### 6.2 场景二：增量提单（合并历史用户）

**步骤**：
1. API已运行，user1和user2已有Token
2. 用户需要新增user3和user4
3. 调用 `GET /dss/apiservice/history/users?apiId=1` 查询历史用户
    - 返回：["user1", "user2"]
4. 用户填写增量提单：
   ```json
   {
       "submitApiInfos": [{"apiId": 1, "apiVersionId": 200}],
       "approvalName": "订单查询API增量授权",
       "applyUser": "user3,user4",
       "incrementalMode": true,
       "duration": "30"
   }
   ```
5. 系统自动合并：历史用户["user1", "user2"] + 新增用户["user3", "user4"]
6. 调用 `POST /dss/apiservice/submit` 提单
7. DM审批通过后，用户在页面点击"刷新状态"按钮
8. 调用 `GET /dss/apiservice/approvalRefresh?approvalNo=xxx` 接口
9. 系统自动为user1、user2、user3、user4生成Token（已实现）

## 十二、核心原则说明

### 12.1 增量授权的核心逻辑

**关键原则**：
1. **版本隔离**：每个API版本有独立的Token集合
2. **手动刷新生成Token**：审批通过后，用户在页面点击"刷新状态"按钮，调用 `approvalRefresh` 接口生成Token（已实现）
3. **用户合并**：增量模式下，自动合并历史用户 + 新增用户（去重）
4. **保留原始信息**：在增量授权模式下，保存用户填写的原始授权用户信息（不包含历史用户），用于前端展示和审计

### 12.2 Token生成的业务逻辑

**场景对比**：

| 场景 | applyUser填写 | 历史user1 | 历史user2 | 新增user3 | 结果 |
|------|-------------|----------|----------|----------|------|
| 首次提单 | user3 | - | - | 生成Token | user3获得授权 |
| 增量提单 | user3,user4 | 生成Token | 生成Token | 生成Token | 所有用户获得授权 |

**重要说明**：
- 增量模式下，总是合并历史用户 + 新增用户
- 不区分历史用户和新增用户，统一生成Token
- 所有用户都获得新Token，旧Token被禁用
