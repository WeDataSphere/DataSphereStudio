# 自动阅读报表数字助手技术设计方案（最终版）

## 1. 总述

### 1.1 需求与目标

#### 1.1.1 业务背景
业务用户日常通过邮件接收多周期（小时报、日报、月报等）业务指标报表，依赖报表数据掌握业务状况、识别异常、分析原因并制定策略。当前人工阅读报表存在效率低、易遗漏关键信息等问题，亟需通过自动化工具提升报表处理效率。

#### 1.1.2 核心目标
1. 自动生成报表文字总结（含综述与异常识别）并推送至用户，替代人工阅读。
2. 支持用户自定义总结模板，满足个性化输出需求。
3. 建立指标基线体系，实现异常自动探测与推送（优先级：高）。
4. 提供历史报表结论查询能力，支持业务回溯分析。
5. 优化系统效率，对使用系统模板的用户共享综述结果，减少冗余计算与存储。


### 1.2 用户故事
- 业务经理："每天早上收到10+份日报，需逐行核对数据，希望8点前收到AI总结的核心结论和异常提醒，节省2小时报表分析时间。"
- 运营专员："月报格式固定但AI总结不符合汇报习惯，希望自定义模板让结论按'核心指标-环比变化-风险点'结构输出。"
- 数据分析师："需快速定位异常指标的历史波动规律，希望系统能存储异常记录并支持基线调整。"
- 系统管理员："大量用户使用相同模板，希望减少重复计算，降低大模型调用成本。"


## 2. 关联影响分析

### 2.1 依赖系统
| 依赖系统 | 交互方式 | 关键需求 |
|----------------|------------------------------|--------------------------------|
| 报表系统 | 实时HTTP推送/定时API拉取 | 需提供标准化报表元数据（ID、类型、周期、数据） |
| 大模型服务 | API调用（同步/异步） | 支持长文本处理、结构化输出，响应延迟<30s |
| 知数-ChatBI企业微信应用 | 消息推送接口 | 支持文本/卡片消息，需处理消息发送失败重试 |
| 身份认证系统 | Token校验 | 用户模板管理需验证用户权限 |

### 2.2 潜在风险
- 报表系统数据格式变更导致解析失败：需建立格式校验机制与版本兼容策略。
- 大模型服务不稳定：需实现降级策略（返回基础统计结果）与失败重试机制。
- 企业微信消息推送限制：需遵守接口频率限制，批量消息分批次发送。
- 多用户共享结果一致性：需确保系统模板变更时，共享结果能正确更新。


## 3. 系统总体设计

### 3.1 技术架构

#### 3.1.1 技术栈选型
| 类别 | 技术选型 | 选型理由 |
|--------------|-------------------|----------------------------------------|
| 开发语言 | Python | 生态丰富，大模型SDK支持完善 |
| Web框架 | FastAPI | 高性能异步支持，自动生成API文档，适合单体应用快速开发 |
| 数据库 | MySQL | 支持事务与复杂查询，适配结构化数据存储 |
| 缓存 | Redis（可选） | 存储临时作业状态、高频访问的模板数据（小型部署可省略） |
| 容器化 | Docker | 简化部署流程，确保环境一致性 |
| 日志 | Python内置logging + Docker挂载 | 轻量日志收集，通过容器挂载实现宿主机持久化 |

#### 3.1.2 架构分层（单体架构）
1. **接入层**：API接口层（负责报表接收、模板管理、查询等接口暴露）。
2. **业务层**：核心功能模块（流程控制、报表综述、异常识别、结果推送、大模型调用）。
3. **数据层**：MySQL数据库（存储报表数据、模板、基线、作业状态等）。
4. **依赖层**：大模型客户端、企业微信SDK（通过API调用外部服务）。


### 3.2 部署架构
- 采用单体应用部署模式，所有功能模块打包为一个Docker镜像。
- 通过Docker容器运行应用，支持多实例部署在负载均衡后实现简单扩展。
- 日志目录通过Docker Volume挂载至宿主机`/var/log/report-robot/`目录，确保日志持久化。


## 4. 功能模块设计

### 4.1 报表接收模块
#### 4.1.1 核心功能
- 提供标准化HTTP接口（`POST /api/v1/report/receive`）接收报表数据。
- 对输入数据进行格式校验（必填字段、数据类型、报表周期合法性），校验失败返回详细错误日志。
- 解析接收人列表，为每个接收人创建关联记录，初始化作业状态。

#### 4.1.2 接口参数示例
```json
{
  "report_id": "RPT20250723001",
  "report_title": "2025-07-22 电商日报",
  "report_type": "daily",  // 支持hourly/daily/monthly
  "cycle": "2025-07-22",
  "data_content": {
    "订单量": {"value": 1200, "unit": "单"},
    "支付转化率": {"value": 85.5, "unit": "%"},
    "客单价": {"value": 156.8, "unit": "元"}
  },
  "mail_title": "今日业务报表",
  "recipients": ["user1@corp.com", "user2@corp.com"]
}
```


### 4.2 流程控制模块
#### 4.2.1 核心功能
- 基于作业ID实现同步流程编排（通过函数调用链完成模块交互）。
- 作业状态管理：支持待处理、处理中、成功、失败、重试中状态流转，通过数据库字段实时更新。
- 共享结果复用逻辑：对使用系统模板的用户，生成并复用共享综述结果。
- 失败重试机制：对大模型调用失败、推送失败等场景，通过本地重试函数实现有限重试（默认3次，间隔2s）。

#### 4.2.2 流程时序图
```
报表接收 → 生成作业(待处理) → 解析接收人并分类 → 
├→ 系统模板用户 → 检查共享结果 → 复用/生成共享结果 → 关联用户-结果
└→ 自定义模板用户 → 生成专属结果 → 关联用户-结果
结果组装 → 调用推送模块 → 更新作业状态(成功/失败)
```


### 4.3 报表综述模块
#### 4.3.1 核心功能
- 模板驱动的综述生成：结合报表数据与模板提示词，调用大模型生成结论。
- 模板管理：支持系统模板与用户自定义模板的CRUD操作，模板内容存储于数据库。
- 共享结果管理：为系统模板用户生成共享结果，减少重复计算。

#### 4.3.2 模板识别逻辑
1. 优先匹配用户为当前报表类型绑定的自定义模板（如用户为"电商日报"设置专属模板）。
2. 无自定义模板时，根据报表类型（如日报/月报）匹配系统默认模板。
3. 系统模板示例（日报）：
```
请基于以下报表数据，按「核心指标总览（3项关键指标）→ 环比变化分析→ 今日亮点」结构生成综述，字数控制在200字内。
数据：{{报表数据}}
周期：{{报表周期}}
```

#### 4.3.3 共享结果生成规则
- 首次处理某报表+系统模板组合时生成共享结果。
- 系统模板更新后，自动触发共享结果重新生成。
- 共享结果与用户通过关联表建立映射，避免内容冗余存储。


### 4.4 异常识别模块
#### 4.4.1 基线建立
- 静态基线：用户可手动配置指标阈值（如"订单量<500单为异常"），存储于`metric_baseline`表。
- 动态基线：基于历史数据自动计算（支持移动平均、3σ原则算法），小型部署可简化为"近7天均值±20%"规则。
    - 特殊日期处理：支持手动标记节假日/大促日，计算基线时自动排除。

#### 4.4.2 异常识别逻辑
1. 数据预处理：清洗报表数据（去重、补全缺失值）。
2. 多维度校验：
    - 数值异常：指标超出基线阈值。
    - 趋势异常：指标环比/同比波动超预设比例（如>20%）。
    - 规则异常：违反业务规则（如"退款率>订单量5%"）。
3. 异常分级：按严重程度分为警告（轻微波动）、异常（显著偏离）、紧急（关键指标崩溃）。


### 4.5 结果推送模块
#### 4.5.1 推送方式
- 企业微信应用消息：支持文本消息（简洁结论）与卡片消息（含综述+异常列表+报表链接）。
- 批量推送处理：当收件人>5人时，采用循环调用推送接口（每次间隔1s），避免触发频率限制。

#### 4.5.2 推送保障
- 状态记录：推送结果（成功/失败）实时更新至`report_push_log`表，失败时记录错误日志。
- 失败处理：推送失败的消息加入本地重试队列，随下一次作业触发时重试。


### 4.6 大模型调用模块
#### 4.6.1 核心功能
1. **多模型支持**：统一接口封装不同大模型服务商（如OpenAI、文心一言、通义千问）的SDK。
2. **提示词管理**：根据报表类型和模板动态生成大模型输入。
3. **密钥管理**：安全存储和轮换大模型API密钥，支持多密钥负载均衡。
4. **调用优化**：实现异步调用、超时控制、结果缓存和错误重试机制。

#### 4.6.2 适配器模式实现
通过适配器模式封装不同大模型的调用差异，对外提供统一接口：
```python
class LLMAdapter(ABC):
    @abstractmethod
    def generate(self, prompt: str, max_tokens: int = 1000) -> str:
        pass

class OpenAIAdapter(LLMAdapter):
    # OpenAI API实现...

class BaiduAdapter(LLMAdapter):
    # 文心一言API实现...

class LLMManager:
    def __init__(self):
        self.adapters = {}  # 模型名称 -> 适配器实例
    
    def register_model(self, model_name: str, adapter: LLMAdapter):
        self.adapters[model_name] = adapter
    
    def generate(self, model_name: str, prompt: str, ...) -> str:
        # 调用适配的模型生成结果...
```

#### 4.6.3 密钥管理方案
- **存储**：API密钥加密存储在数据库中，使用时从环境变量加载主密钥进行解密。
- **轮换**：支持定期自动轮换API密钥，通过管理界面上传新密钥。
- **负载均衡**：对同一服务商配置多个API密钥时，自动进行负载分发。


### 4.7 日志模块
#### 4.7.1 日志配置
- 日志级别：支持DEBUG（开发环境）、INFO（生产环境）、ERROR级别日志。
- 日志内容：包含作业ID、模块名称、时间、日志信息，关键步骤（如大模型调用、异常识别）强制打印详细日志。
- 日志路径：应用内日志目录为`/app/logs/`，通过Docker挂载至宿主机`/var/log/report-robot/`，日志文件按日分割。

## 7. 非功能性设计

### 7.1 安全
- 接口认证：所有外部接口通过企业微信Token验证（集成企业内部身份认证逻辑）。
- 数据加密：敏感数据（如大模型API密钥）存储时采用AES加密，配置在环境变量中。
- 权限控制：用户仅能管理自己创建的模板，查看自己有权限的报表结论。

### 7.2 性能
- 异步处理：采用FastAPI的`BackgroundTasks`实现报表处理异步化，避免接口阻塞。
- 共享结果复用：对系统模板用户复用共享结果，减少大模型调用次数（预计减少60%+调用量）。
- 数据库优化：为高频查询字段（如report_id、job_id）建立索引，减少查询耗时。
- 资源控制：限制并发处理的作业数量（通过配置文件设置，默认20个并发）。

### 7.3 高可用
- 多实例部署：通过Docker启动多个应用实例，前端挂负载均衡（如Nginx）实现简单冗余。
- 降级策略：大模型服务不可用时，自动切换至纯规则引擎生成基础结论（仅统计+异常标记）。
- 熔断机制：当某个大模型服务连续失败超过3次时，自动熔断该服务5分钟，期间使用备用模型。
- 数据备份：MySQL每日自动备份（通过crontab脚本），备份文件存储于宿主机。

### 7.4 日志管理
- 日志输出：按模块划分日志（如`report_receive.log`、`summary.log`、`push.log`），包含时间、级别、作业ID、详细信息。
- Docker挂载：容器内日志目录`/app/logs/`挂载至宿主机`/var/log/report-robot/`，确保容器重启后日志不丢失。
- 日志轮转：通过Python日志配置实现日志按大小轮转（单个文件最大100MB，保留5个备份）。

### 7.5 可扩展性
- 模块化设计：各模块通过接口通信，支持独立升级（如替换大模型服务）。
- 配置中心：采用本地配置文件或轻量配置服务管理系统参数（如基线算法、推送频率），支持动态生效。


## 8. 测试策略

### 8.1 功能测试
- 单元测试：覆盖核心算法（如动态基线计算、异常识别规则、共享结果复用逻辑）。
- 集成测试：验证报表接收→流程控制→推送全链路正确性。
- 场景测试：
    - 多接收人混合场景（部分用系统模板，部分用自定义模板）
    - 系统模板更新后共享结果重新生成
    - 大模型超时、报表数据格式错误等边界场景

### 8.2 性能测试
- 并发测试：验证系统在50 TPS报表接收下的响应时间（目标<1s）。
- 负载测试：模拟1000个接收人的大型报表处理，验证共享结果机制的效率提升。
- 稳定性测试：持续8小时运行，监控作业成功率（目标>99.5%）。

### 8.3 效果测试
- 综述准确性：人工评估AI综述与实际报表的一致性（目标准确率>90%）。
- 异常识别率：对比AI识别结果与人工标注，计算召回率（目标>85%）。
- 共享结果一致性：验证不同用户获取的共享结果是否完全一致。

## 10. 总结
本方案基于单体架构设计，通过模板驱动的大模型调用实现报表自动阅读与异常识别，并创新性地引入共享结果机制，为使用系统模板的用户复用综述结果，显著降低计算成本与存储冗余。系统支持用户自定义模板，满足个性化需求，同时通过完善的异常基线体系提升异常识别准确性。

方案在设计上平衡了功能完整性与实现复杂度，通过Docker容器化部署简化运维，通过多实例部署和降级策略保障高可用性。整体架构具备良好的可扩展性，可随业务需求增长逐步优化升级。

通过本系统的实施，预计可减少业务用户80%的报表阅读时间，提升异常发现效率，为业务决策提供及时支持。
