## 一、增量授权测试用例

### TC-E3-001：增量授权 - 首次提单无历史用户

**来源**：需求文档 - E3增量授权核心功能

**测试类型**：功能测试

**前置条件**：
- 存在API(ID=100, 版本ID=1001)
- 该API没有历史审批记录

**测试步骤**：
1. 用户首次提单并填写授权用户"user1,user2"
2. 审批通过后调用审批刷新接口
3. 查询生成的Token列表

**预期结果**：
- 为user1生成Token
- 为user2生成Token
- Token状态为有效
- 不执行历史用户合并

**测试数据**：
```json
{
  "submitApiInfos": [{"apiId": 100, "apiVersionId": 1001}],
  "approvalName": "首次授权",
  "applyUser": "user1,user2",
  "duration": "30",
  "workspaceId": 180
}
```

**优先级**：P0
**标签**：@smoke @critical

### TC-E3-002：增量授权 - 自动合并历史用户

**来源**：需求文档 - E3增量授权核心功能，设计文档核心流程

**测试类型**：功能测试

**前置条件**：
- 存在历史审批记录：
  - API ID=100, 版本ID=1001, 审批单号="uuid-v1", 授权用户="user1,user2", 状态=成功
- 创建新版本(ID=100, 版本ID=1002)

**测试步骤**：
1. 用户提单并只填写新增用户"user3,user4"
2. 审批通过后调用审批刷新接口
3. 查询生成的Token列表

**预期结果**：
- 系统自动查询历史审批单
- 自动合并历史用户user1和user2
- 为user1生成新版本Token
- 为user2生成新版本Token
- 为user3生成Token
- 为user4生成Token
- 历史版本(1001)的Token被禁用
- 新版本(1002)的Token有效
- 最终授权用户：user1,user2,user3,user4

**测试数据**：
```json
{
  "submitApiInfos": [{"apiId": 100, "apiVersionId": 1002}],
  "approvalName": "增量授权",
  "applyUser": "user3,user4",
  "duration": "30",
  "workspaceId": 180
}
```

**优先级**：P0
**标签**：@smoke @critical

### TC-E3-003：批量API申请时增量授权 - 跨API历史用户合并

**来源**：需求文档 - E1批量提单功能，E3增量授权核心功能

**测试类型**：功能测试

**前置条件**：
- 存在以下API及其历史记录：
  - API ID=100: 订单查询API, 当前版本ID=1002, 历史版本ID=1001, 历史授权用户=user1,user2, 状态=成功
  - API ID=101: 用户管理API, 当前版本ID=2002, 历史版本ID=2001, 历史授权用户=user3,user4, 状态=成功
  - API ID=102: 数据统计API, 当前版本ID=3002, 无历史审批记录

**测试步骤**：
1. 用户批量提单并填写以下信息：
   - API列表(ID=100,101,102)
   - 授权用户：user5,user6
   - 审批单名称：三API联合授权
2. 审批通过后调用审批刷新接口
3. 分别查询三个API的Token列表

**预期结果**：
- 订单查询API(ID=100)的最终授权用户为user1,user2,user5,user6（4个用户）
- 用户管理API(ID=101)的最终授权用户为user3,user4,user5,user6（4个用户）
- 数据统计API(ID=102)的最终授权用户为user5,user6（2个用户，无历史用户）
- 每个API的历史版本Token被禁用
- 新Token状态为有效

**测试数据**：
```json
{
  "submitApiInfos": [
    {"apiId": 100, "apiVersionId": 1002},
    {"apiId": 101, "apiVersionId": 2002},
    {"apiId": 102, "apiVersionId": 3002}
  ],
  "approvalName": "三API联合授权",
  "applyUser": "user5,user6",
  "duration": "30",
  "workspaceId": 180,
  "backgroundDesc": "批量API增量授权测试"
}
```

**优先级**：P0
**标签**：@smoke @critical @integration

## 二、重复授权防护测试用例

### TC-E5-001：重复授权防护 - 重复调用不重复生成Token

**来源**：需求文档 - E5重复授权防护，设计文档核心流程

**测试类型**：功能测试

**前置条件**：
- 存在审批单(审批单号="uuid-001")
- 审批单状态为"成功"
- 该审批单已生成Token记录

**测试步骤**：
1. 用户第一次调用审批刷新接口 approvalRefresh，传入approvalNo="uuid-001"
2. 验证Token生成成功
3. 用户再次调用审批刷新接口（相同的approvalNo）
4. 查询数据库Token记录

**预期结果**：
- 第一次调用正常生成Token
- 第二次调用检测到该审批单已存在Token并跳过重复插入
- 返回成功状态
- 数据库中不存在重复的Token记录（每用户每版本只有一条有效Token）

**测试数据**：
```
第一次调用：
GET /dss/apiservice/approvalRefresh?approvalNo=uuid-001

第二次调用：
GET /dss/apiservice/approvalRefresh?approvalNo=uuid-001
```

**优先级**：P0
**标签**：@smoke @critical

## 测试执行建议

### 测试环境准备

1. **数据库准备**
   - 准备测试数据：API、API版本、审批单、Token记录
   - 准备测试用户：user1、user2、user3、user4、user5、user6、user7

2. **Mock服务**
   - Mock DM审批系统接口
   - 模拟审批通过/失败场景

3. **测试数据清理**
   - 每个测试用例执行前后清理测试数据
   - 避免测试数据互相影响

### 执行顺序

1. **阶段1：冒烟测试**（P0）
   - 执行所有P0优先级的测试用例
   - 验证核心功能正常

2. **阶段2：增量授权验证**

   - TC-E3-004: 验证用户去重
   - TC-E3-003: 验证批量API跨API独立处理
   - TC-E3-005: 验证批量申请API进行增量授权

3. **阶段3：配置与防护验证**
   - TC-E4-001: 验证历史配置保留
   - TC-E5-001: 验证重复授权防护
